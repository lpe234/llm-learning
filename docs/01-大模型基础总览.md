# 第 1 周：大模型基础总览

## 分享定位

本周的目标是建立基础认知，不是做大模型开发培训，也不是系统讲解某个框架。重点回答：

> 大模型能做什么？不能做什么？为什么会犯错？如何给它提供信息？如何让它使用外部能力？

内容以概念和演示为主。大家已经在使用的功能，不展开底层实现；容易产生误解、又会影响后续理解的内容，重点讲清楚。

## 一、重点讲清楚的内容

### 1. 能力、边界与概率模型

- 大模型擅长文本生成、总结、改写、分类、信息抽取和一定程度的推理
- 大模型不等于数据库、搜索引擎或事实核验系统
- 大模型的回答本质上是基于概率生成下一个 Token
- 概率高不代表事实一定正确
- 同一个问题可能因为上下文、采样和表达方式不同而得到不同答案

### 2. 为什么会产生幻觉

重点让大家理解：

- 模型的目标是生成合理的回答，不是保证每句话都是真实的
- 模型可能缺少最新信息或内部业务知识
- 问题本身不清楚时，模型可能自行补全条件
- 上下文中存在错误或冲突信息时，模型可能据此继续推理
- 语言表达流畅，不等于内容经过事实验证

### 3. Token、参数量与小模型

- Token 是模型处理文本的基本单位，不完全等同于字或词
- 输入 Token、输出 Token 会影响上下文长度、速度和费用
- 8B、32B 中的 B 是 Billion，表示参数量大约为 80 亿、320 亿
- 参数量不是知识量，也不是模型能力的唯一标准
- 小模型适合低成本、低延迟、本地部署、隐私场景和固定任务
- 大模型与小模型可以按任务复杂度、数据敏感性、响应速度和成本进行选择

可以简单提到 Dense 和 MoE，但不展开模型结构细节。需要提醒大家：MoE 模型的总参数量和单次实际激活参数量可能不同。

### 4. Prompt 与上下文

- Prompt 是给模型的任务说明和约束
- 上下文是模型本次回答时能够看到的全部信息
- Prompt 只是上下文的一部分
- 上下文不等于长期记忆
- RAG 的本质，是把检索到的外部资料临时加入上下文

## 二、概念介绍即可的内容

### 1. 多模态、Vision 和 Thinking

- 多模态：模型可以处理文字以外的图片、音频、视频等信息
- Vision：模型能够接收和理解图片、截图等视觉输入
- Thinking：模型在输出答案前进行更复杂的分析、推理或规划
- Vision + Thinking：模型既能看图，也能基于图像内容进行分析和推理

这里不讨论具体模型内部如何实现，只通过一张 UI 截图或一张流程图做演示。

### 2. Tools

Tools 是提供给模型使用的外部能力，例如：

- 查询项目状态
- 查询数据库
- 搜索网页
- 读取文件
- 调用业务接口
- 计算或执行程序

模型支持 Tools，并不意味着模型自己拥有这些能力，而是调用它的应用允许模型请求这些能力。

### 3. Skills

Skill 可以理解为一套针对某类任务的说明、规则、模板和参考资料，用来让模型更稳定地完成工作。

例如“生成项目周报 Skill”可以规定：

- 周报的输出格式
- 必须包含哪些字段
- 如何描述风险
- 哪些内容需要人工确认

本周只讲概念和例子，不讲具体平台的 Skill 加载机制。

## 三、重点演示：函数调用

### 1. 函数调用是什么

函数调用是让模型以结构化方式提出“调用某个函数，并传入这些参数”的请求。

模型通常不直接执行函数，真正执行函数的是外部应用程序。

### 2. 函数调用的完整过程

```text
用户提出问题
    ↓
模型判断是否需要工具
    ↓
模型输出函数名和参数
    ↓
应用程序校验参数并真正执行函数
    ↓
应用程序把函数结果返回给模型
    ↓
模型生成最终回答
```

### 3. 建议演示

演示一个 `query_project_status(project_id)` 函数：

1. 用户询问某个项目进展
2. 模型判断需要调用查询函数
3. 模型输出项目编号参数
4. 程序执行查询并返回结果
5. 模型整理成自然语言摘要

演示重点是让大家看到：模型负责理解和决策，程序负责真实执行。

## 四、MCP：让外部能力更容易接入

### 1. MCP 是什么

MCP（Model Context Protocol）是一种连接 AI 应用与外部数据、工具和提示模板的开放协议。

它不是模型，也不是 Agent 框架，而是让不同 AI 应用以统一方式发现和使用外部能力。

MCP 中常见的能力包括：

- Tools：模型可以调用的函数或操作
- Resources：提供给模型或应用的上下文数据
- Prompts：可复用的提示模板

### 2. MCP 和函数调用的关系

可以这样理解：

- 函数调用：一次具体的模型调用机制
- MCP：把工具、数据和提示以统一协议提供给不同客户端
- MCP Server：提供工具和数据的一方
- MCP Client：连接 MCP Server 的客户端组件
- Host：承载 AI 能力的应用，例如聊天应用、IDE 或内部助手

函数调用解决“模型如何请求执行一个函数”，MCP 进一步解决“这个函数由谁提供、如何被发现、如何跨应用复用”。

## 五、MCP 的两种通信方式

MCP 使用 JSON-RPC 表达消息，当前标准传输方式主要包括本地 `stdio` 和 Streamable HTTP。

### 1. 本地通信：stdio

本地客户端启动 MCP Server 子进程：

```text
AI 应用启动 MCP Server 子进程
        ↓
客户端通过 stdin 发送 JSON-RPC 消息
        ↓
MCP Server 通过 stdout 返回 JSON-RPC 消息
```

特点：

- MCP Server 通常运行在本机
- 不需要开放网络端口
- 适合本地文件、开发工具和个人环境
- 认证信息通常由本地环境变量或本地配置提供
- stdout 只能输出合法的 MCP 消息，普通日志应写到 stderr

### 2. 远程通信：Streamable HTTP

远程 MCP Server 作为独立服务运行，通过 HTTP 端点接收和返回 JSON-RPC 消息：

```text
AI 应用 / MCP Client
        ↓ HTTP POST / GET
远程 MCP Server
        ↓
工具、网页、数据库或其他业务服务
```

特点：

- 服务可以独立部署，多个客户端可以连接
- 客户端通过 HTTP POST 发送 JSON-RPC 消息
- 服务端可以通过 JSON 或事件流返回结果
- 适合团队共享、云端服务和跨网络接入
- 需要考虑 HTTPS、鉴权、会话和访问控制

本地 `stdio` 更像“应用启动一个本地插件”，HTTP 更像“应用连接一个远程服务”。

## 七、鉴权与安全

这一部分只讲基本认知，但必须讲到，因为 MCP 工具可能具备真实的数据访问和操作能力。

### 1. 本地 MCP 的安全

- 不要默认信任网上下载的 MCP Server
- 检查它能访问哪些文件、网络和环境变量
- 使用最小权限，不要随意授予整个磁盘或全部项目目录
- 密钥通过环境变量或安全配置提供，不要写入代码和日志
- stdout 不要输出调试日志，避免破坏 MCP 消息

### 2. HTTP MCP 的安全

- 使用 HTTPS 保护通信
- 对远程服务进行身份认证和权限校验
- 不把访问令牌放在 URL 查询参数中
- 校验 Token 是否确实签发给当前 MCP Server
- 对敏感操作保留人工确认
- 设置超时、限流、调用日志和错误处理
- HTTP 服务需要校验 Origin，避免 DNS rebinding 等攻击

### 3. 工具本身的安全

- 工具参数必须校验，不能完全相信模型生成的参数
- 查询、写入、删除、发送消息等操作应区分权限
- 高风险操作尽量采用“模型建议 + 人工确认”
- 网页抓取结果属于不可信内容，网页中的指令不能直接当作系统指令执行
- 对 Fetch 类服务应限制可访问的地址、响应大小和网络范围，避免被利用访问内部服务

安全边界可以总结为：

> 模型可以提出调用请求，但最终能不能调用、能调用什么、调用结果能产生什么影响，都必须由应用和权限系统控制。
